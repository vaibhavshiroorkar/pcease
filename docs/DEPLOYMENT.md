# PCease Deployment & Integration Guide

How the pieces connect in production, and how to build your own price-fetching API.
Everything here is grounded in the real config (`backend/app/config.py`,
`backend/render.yaml`, `frontend/vercel.json`, `frontend/src/services/api.js`).

```
  Browser
     │  https
     ▼
  Vercel  (frontend, static React build)
     │  VITE_API_URL  ->  https://<your-api>.onrender.com/api
     ▼
  Render  (backend, FastAPI / uvicorn)
     │  SUPABASE_URL + SERVICE_KEY        │  GEMINI / ANTHROPIC key
     ▼                                    ▼
  Supabase (Postgres + auth data)      AI provider (agent + advisor)
     ▲
     │  upserts prices
  Price worker  (your own scraper/API - optional, see last section)
```

The four services are linked by **four values**, set them and everything talks:

| Where | Variable | Value |
|-------|----------|-------|
| Vercel (frontend) | `VITE_API_URL` | `https://<your-api>.onrender.com/api` |
| Render (backend) | `FRONTEND_URL` | `https://<your-app>.vercel.app` (for CORS) |
| Render (backend) | `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` | from Supabase project settings |
| Render (backend) | `GEMINI_API_KEY` and/or `ANTHROPIC_API_KEY` | from the AI provider |

## 1. Supabase (database)

1. Create a project at supabase.com. Note the **Project URL** and, under
   *Project Settings -> API*, the **anon** key and the **service_role** key.
2. Open the **SQL Editor** and run the migrations **in this order** (each is
   idempotent / safe to re-run):
   1. `backend/supabase_migration.sql`   (core schema: categories, components, prices, users, builds, forum)
   2. `backend/social_migration.sql`      (likes, favourites, follows, profiles)
   3. `backend/watchlist_migration.sql`   (watchlist)
   4. `backend/forum_followup_migration.sql` (threaded replies + `users.is_deleted`)
   5. `backend/support_tickets_migration.sql` (tickets)
3. **Seed the catalog** (vendors, components, prices). Locally, with the service
   key exported:
   ```bash
   cd backend
   pip install -r requirements.txt
   set SUPABASE_URL=...          # PowerShell: $env:SUPABASE_URL="..."
   set SUPABASE_SERVICE_KEY=...
   python seed_supabase.py
   ```
   This upserts the vendors (PrimeABGB, EliteHubs, MDComputers, Vishal Peripherals,
   Computech Store, TLG Gaming, Vedant Computers, ITDepot) and the component catalog.

Keep the **service_role key server-side only** (Render). Never ship it to the
frontend.

## 2. Render (backend / FastAPI)

The repo ships a blueprint at `backend/render.yaml`. Easiest path:

1. Render dashboard -> **New -> Blueprint** -> connect this repo -> pick `render.yaml`.
2. It creates a web service with:
   - `rootDir: backend`
   - build: `pip install -r requirements.txt`
   - start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
3. Set the `sync: false` env vars in the dashboard:
   - `SUPABASE_URL`, `SUPABASE_KEY` (anon), `SUPABASE_SERVICE_KEY` (service_role)
   - `GEMINI_API_KEY` and/or `ANTHROPIC_API_KEY`
   - `FRONTEND_URL` = your Vercel URL (used for CORS; see `app/main.py`)
   - `SECRET_KEY` is auto-generated by the blueprint; `DEBUG` defaults off in prod
4. If you use the Claude agent (default `LLM_PROVIDER=claude`), also set
   `ANTHROPIC_API_KEY`. To use Gemini instead, set `LLM_PROVIDER=gemini` and
   `GEMINI_API_KEY`. The advisor "ask"/Compare-summary uses `GEMINI_API_KEY` when set.

Health check is `/`. First request after idle is slow on the free plan (cold start).

## 3. Vercel (frontend / React + Vite)

1. Import the repo, set **Root Directory** to `frontend`.
2. Framework preset: Vite. Build: `npm run build`, output `dist`.
3. Add **one** env var: `VITE_API_URL = https://<your-api>.onrender.com/api`
   (Vite inlines `VITE_*` at build time, so redeploy after changing it).
   The frontend reads it in `services/api.js`: `API_BASE = import.meta.env.VITE_API_URL || '/api'`.
4. `frontend/vercel.json` already handles SPA rewrites. Done.

## 4. AI provider

- **Agent** (Builder/Advisor agentic chat): `LLM_PROVIDER` = `claude` or `gemini`,
  with the matching `ANTHROPIC_API_KEY` / `GEMINI_API_KEY`.
- **Advisor "ask" + Compare AI verdict**: use `GEMINI_API_KEY` (gemini-1.5-flash).
  With no key they fall back gracefully (the Compare verdict shows the comparative
  message; the advisor shows a templated answer).
- If you mean a third-party "AI/ML API" gateway rather than Google/Anthropic
  directly: point the SDK base URL at the gateway and keep the key in the same env
  var. The app only needs a key + a model name.

## Linking checklist (do these last)

- [ ] Supabase migrations run + `seed_supabase.py` executed.
- [ ] Render env has Supabase URL + service key + AI key + `FRONTEND_URL`.
- [ ] Vercel env has `VITE_API_URL` pointing at the Render `/api` base, redeployed.
- [ ] Open the Vercel URL: Browse should list components with prices; Advisor chat
      should respond; sign-up/login should work (writes to Supabase `users`).
- [ ] If Browse is empty: the seed didn't run or `VITE_API_URL` is wrong.
- [ ] If you see CORS errors: `FRONTEND_URL` on Render must match the Vercel origin.

## 5. Building your own price-fetching API

Today prices are seeded static values. To make them live, run a **price worker**
that periodically writes fresh prices into Supabase. The app already reads from
`component_prices`, so you only need to keep that table current. No app code changes
are required.

### How prices are stored

`component_prices` rows: `component_id`, `vendor_id`, `price`, `in_stock`, `url`,
`updated_at`. The frontend's lowest-price / best-vendor logic just reads these.

### Architecture (keep it a separate service)

Do **not** scrape inside the FastAPI request path (too slow, gets you rate-limited).
Run a scheduled worker:

- **Render Cron Job** (separate service, same repo) or **GitHub Actions** on a
  schedule, or **Supabase pg_cron + Edge Function**. Any of them can hold the
  service key and write to Supabase.

### Where prices come from (pick per vendor, in order of preference)

1. **Official / affiliate feeds or APIs** (Amazon PA-API, vendor data feeds). Most
   reliable and ToS-clean. Often gives a product URL + price you can map directly.
2. **Structured data on the product page** (JSON-LD `Product`/`Offer`, or a public
   internal JSON endpoint the site's own frontend calls). Cheap to parse, stable.
3. **HTML scraping** as a last resort. Brittle and must respect each site's
   `robots.txt` and Terms of Service. Cache aggressively, throttle, identify your
   bot, and stop if asked. This is a legal/ethical call you own.

### Mapping: vendor product -> your catalog

The hard part is matching a vendor's listing to a `components.id`. Practical approach:

- Add a `vendor_skus` mapping table: `(component_id, vendor_id, vendor_url, sku)`.
  Curate it once per product (or fuzzy-match on name + brand to seed it), then the
  worker just refreshes prices for known URLs. This avoids re-matching every run.

### Worker skeleton (Python)

```python
# price_worker.py  (run on a schedule; needs SUPABASE_URL + SUPABASE_SERVICE_KEY)
import os, datetime, httpx
from supabase import create_client

db = create_client(os.environ["SUPABASE_URL"], os.environ["SUPABASE_SERVICE_KEY"])

def fetch_price(url: str) -> dict | None:
    """Return {'price': int, 'in_stock': bool} for one vendor product URL.
    Prefer an official API/JSON-LD here; HTML parsing is the fallback."""
    r = httpx.get(url, headers={"User-Agent": "PCeasePriceBot/1.0 (+contact)"}, timeout=20)
    r.raise_for_status()
    # ... parse JSON-LD Offer / vendor JSON and return the price + stock ...
    return None

def run():
    skus = db.table("vendor_skus").select("component_id, vendor_id, vendor_url").execute().data or []
    now = datetime.datetime.now(datetime.timezone.utc).isoformat()
    for s in skus:
        try:
            p = fetch_price(s["vendor_url"])
            if not p:
                continue
            db.table("component_prices").upsert({
                "component_id": s["component_id"],
                "vendor_id": s["vendor_id"],
                "price": p["price"],
                "in_stock": p["in_stock"],
                "url": s["vendor_url"],
                "updated_at": now,
            }, on_conflict="component_id,vendor_id").execute()
        except Exception as e:
            print("skip", s["vendor_url"], e)

if __name__ == "__main__":
    run()
```

Add a unique constraint on `component_prices(component_id, vendor_id)` so `upsert`
with `on_conflict` updates in place instead of duplicating rows.

### Price history (for the graph)

The price chart (`/components/{id}/price-history`) is currently synthesized. To make
it real, have the worker also append a row per run to a `price_history` table
(`component_id, vendor_id, price, captured_at`), then change that endpoint to read
from it. Daily granularity is plenty.

### Don'ts

- Don't put scraping in the user request path.
- Don't ship the service key to the browser or commit it.
- Don't ignore a vendor's ToS / robots.txt; prefer their API or feed.
